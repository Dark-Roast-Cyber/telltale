# ADR 0009: Tamper detection by default, tamper prevention by choice

Status: Accepted. Amends the consequences of
[ADR 0008](0008-detect-only-by-default.md): its statement that
`settings --fail-closed` is harmless in detect-only mode is superseded. A
hook command that cannot start at all (a missing binary) is blocked by Claude
Code under `onFailure: "block"`, whatever mode the hook would have run in.

## Context

Telltale is a monitoring and detection tool first, and enforcement is an
option. Hooks carried four protections of themselves, switched in different
places:

- the self-protection rules (`tth.tamper.*`), on by default;
- a lock that came with those rules: no override, policy, rule file or rule
  package could change or disable one, and content that tried was invalid
  configuration;
- Claude Code's `onFailure: "block"`, generated by `settings --fail-closed`,
  which the quick start used;
- the Codex exec-policy rules, printed by `codex-cli execpolicy`.

The lock made the rules the one part of the rule set an operator could not
tune, short of turning all of them off. The last two act inside the harness
without the hook, so they can block a tool call of an installation that is
set to observe.

## Decision

1. **Detection stays on.** The self-protection rules load by default and are
   rules like any other: recorded in detect-only mode, returned under
   `hooks.mode: enforce`.
2. **The lock is a setting, off by default:**
   `hooks.tamper_prevention.enabled`. Without it an override, a policy or a
   replacement in a managed tier applies to a self-protection rule as to any
   bundled rule. With it the previous behavior holds unchanged. It needs
   `hooks.self_protection_rules`; asking for it without them is invalid
   configuration.
3. **Protections installed into a harness stay explicit and separate.**
   `settings --fail-closed` and `codex-cli execpolicy` are unchanged, no
   command installs them, `hooks.mode: enforce` does not imply them, and the
   documented default install uses neither. `telltale hooks check` lists
   them per harness. The setting does not control them, because a runtime
   setting cannot remove what a harness applies on its own.
4. **An operator's override is not tampering.** Telltale cannot tell an
   administrator's edit of a configuration file from an agent's edit made as
   the same OS user, so whoever can write a config root the hook reads is the
   operator. The agent's write is a tool call, which the rules detect.

## Rejected

- **Making the self-protection rules record-only under enforcement unless
  tamper prevention is on.** It would stop existing enforcing deployments
  from denying writes to their own configuration on upgrade, with nothing on
  screen.
- **Keeping the lock on by default.** The lock was never a boundary against
  an agent that can write the configuration: the same files hold
  `hooks.self_protection_rules` and `hooks.mode`. It did stop operators
  tuning one part of the rule set.
- **One switch that also turns the harness-installed protections on or
  off.** They live in files Telltale does not write, and a switch that
  claimed to remove them would claim something it cannot do.
- **Reading harness files in `check` to report what is installed.** A partial
  answer (user settings but not managed ones) reads as "not installed".
  Reporting belongs with managed installation.

## Consequences

- A configuration that names a `tth.tamper.` rule in an override, or drops
  the rules by policy, loaded as invalid before and now applies.
- An installation of an earlier development build had the lock whenever the
  rules were on. After this change it has it only with
  `hooks.tamper_prevention.enabled: true`: its configuration loads as before
  and detects as before, but content added later can tune or drop the rules.
  `telltale hooks check` prints the lock's state and how many self-protection
  rules run.
- The lock, like enforcement, is as strong as the write protection of the
  files that hold it. A boundary that separates an administrator from the
  agent belongs to managed deployment.
