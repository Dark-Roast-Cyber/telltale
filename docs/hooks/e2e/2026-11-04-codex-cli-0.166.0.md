# Real-harness results: Codex CLI 0.166.0, 2026-11-04

Run: `scripts/hooks/harness/codex-cli-e2e.py`, all 24 scenarios, telltale-hooks release
build of commit `a5b5665`, Telltale `0249eafb`, the real
`@openai/codex` 0.166.0 binary (Linux x86-64 musl), each scenario in a fresh
`CODEX_HOME` and HOME. Raw per-scenario summaries (paths scrubbed):
[`2026-11-04-codex-cli-0.166.0.summary.jsonl`](2026-11-04-codex-cli-0.166.0.summary.jsonl).

The code under test is `a5b5665`. The E2E was not rerun for what follows it,
because none of it touches the hook path: `e670528` adds only these results,
`fa369bf` and `f6786c2` only make `settings` refuse unknown flags (`print_settings`,
its test and one doc line), and `d72b7dc` and the commit that last edited this
paragraph change only this file. The run was outside any sandbox, because the TUI's
app-server daemon and the evaluator need Unix sockets.

**Model: scripted** (`scripts/hooks/harness/mock-model.py` as a custom
Responses-API provider). The tool calls are fixed, so these runs verify how
Codex enforces this adapter's output; they say nothing about how a real model
reacts to a denial. **Real-model run pending** (no OpenAI credits).

Method: the scripted model calls `exec_command` with `touch <canary> &&
<command>`. The canary is ground truth for execution. Hooks are installed
exactly as `telltale hooks codex-cli settings` prints them, the marker rules
(`crates/telltale/tests/hooks/e2e-marker-rules.yaml`) are loaded, and the exec-policy rules
come from `telltale hooks codex-cli execpolicy`. A stand-in `codex` on PATH keeps
nested launches harmless. All runs use
`--dangerously-bypass-approvals-and-sandbox`, the weakest native setting.

Trust differs by scenario. `untrusted` records none and passes no flag. The
`trusted*` scenarios run the documented install with **no bypass flag anywhere**:
the real interactive `codex` in a pty, with the app-server daemon it starts by
default, shows its startup hook review ("9 hooks are new or changed"), the script
sends Down and Enter on "Trust all and continue", Codex writes 9 `trusted_hash`
records through its own config write, and `codex exec` then runs. The script only
pre-seeds the separate directory-trust prompt. Every other scenario passes
`--dangerously-bypass-hook-trust`. Decisions are in-process with
`TELLTALE_HOOKS_EVALUATOR=0`, except `deny-evaluator`, which uses the default
autostart.

The `damaged-*` scenarios need a bad payload from the real Codex, so a wrapper in
front of the hook damages one event's stdin before passing it on, and the scenario
fails if no damage happened. The damaged `Stop` scenarios also fail unless the turn
takes exactly 2 model requests, because an extra one is a continuation prompt.

Findings:

1. Codex honors the adapter's `hookSpecificOutput` deny for the main agent
   and inside a subagent. In the subagent run the child's call carried its
   own `agent_id` and was settled by `SubagentStop`, while the parent's
   later call in the same session ran and settled by its own PostToolUse.
2. A policy `ask` is returned as `deny` (`returned_verdict: deny`) and
   blocks. Codex would run a returned `ask`.
3. An allowed call prints nothing and runs.
4. **Every hook failure fails open**: missing binary, timeout, crash. An
   untrusted hook never runs. No configuration changes this; these rows are
   residual risk, not adapter defects.
5. The exec-policy backstop refused a nested hookless Codex launch with the
   hook absent. It is literal: some shell constructs make Codex match the
   whole script and the rule did not apply.
6. Settlement: each denied call was settled `not_executed / honored` by the
   turn-end event of its own agent, never by another agent's.
7. The documented install enforces: hooks trusted through the real TUI, with
   no bypass flag, honored a deny (`trusted`).
8. Trust is per handler: re-indenting the file and changing another handler
   kept PreToolUse trusted, changing its command text un-trusted it and the call
   ran, and replacing the program at the trusted path kept trust.
9. A real `apply_patch` to a hook file is denied through the runtime's
   normalization and the file is not created; the benign control applies.
10. With the default autostart, the first hook falls back in-process while the
    evaluator starts, and a later deny is served by it and honored.
11. A damaged PreToolUse is blocked with no telemetry record of the call: the hook
    could not read it, so the only trace is the hook's stderr.
12. A damaged `Stop` costs no extra model request, but the denied call in that
    turn settles as `unknown` at SessionEnd rather than `honored`, because the
    event that would establish it was lost. This is the correct accounting.

Why the `damaged-*` rows exist: on the tree before the fix (commit `62a677f`),
`damaged-pre-default` left the canary **present**, so the call ran, and a `Stop` cut
before its name made **3,586 model requests** with the turn never ending, until the
run's time limit stopped it. A first fix that only exited 1 for a named event looped
the same way on that payload (2,979 requests when checked), which is why a payload
naming no event gets a deny on stdout on Codex and not exit 2.

Not exercised here: the `/hooks` browser, a human's terminal, a turn run inside
the TUI (the deny was checked under `codex exec`), `PostToolUse`
`additionalContext`, MCP calls through the adapter, a real model, Windows and
macOS (Codex hook behavior there is unverified), and the same damaged payloads on
real Claude Code or Copilot CLI (those entry points have binary contract tests
only, `tests/cli/hooks_unreadable_payloads.rs`). In-process pipeline build 309-361 ms
and scan 2-15 ms per decision in this run, against a 30 s hook timeout.
