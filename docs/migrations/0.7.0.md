# Migrating to 0.7.0

Status: compatibility guide for published prerelease `v0.7.0-rc.1` (Release ID
`397543935`, source `e2386cb53454a8384449ea0729f0e3b71072006c`). Five-platform
native qualification passed in run `36305581215` using verifier tooling
`c5c955f57a83cbfc7bd9827932a5e7d54a2fd077`. Stable `v0.7.0` is not published;
clean-host qualification and stable promotion remain separate.

The untagged, unpublished `0.7.0-rc.2` tree adds bounded OpenCode tool-result
and patch text and less redundant evaluation work; see
[OpenCode ingestion limits](../opencode-live-ingestion.md). Event3, state format,
stable identities, and the newest-5,000 bootstrap coverage are unchanged.

## Rust embedding changes since RC1

Everything in this section is in the untagged, unpublished `0.7.0-rc.2` tree,
not the published RC1 artifacts. Update your Git pin deliberately and revalidate
the host; RC1 evidence does not qualify these changes. The resulting contract is
in [embedding](../embedding.md); hosts adopting actions should start at
[detailed action scanning](../embedding.md#detailed-action-scanning).

**Errors (Issue #84).** `build` and the `scan_*` methods return the
non-exhaustive `telltale_core::PipelineError` instead of boxed errors. Replace
downcast-based classification with enum matching plus a fallback arm. Functions
returning `Box<dyn Error>` can still use `?`, but explicitly forwarded boxed
results must convert, for example `Ok(pipeline.scan_root(root)?)`. Missing
documents are `InvalidConfiguration`; `Compilation` has an opaque diagnostic
source. Rule content that loads as Rule v1 but that canonical compilation
rejects (for example an unknown severity or a score above 100) now fails
`build()`; it no longer builds a `Pipeline` whose scans all return
`Compilation`. See [typed pipeline errors](../embedding.md#typed-pipeline-errors).

**New scan methods.** `scan_sources` scans exactly the supplied sources (RC1
adopters only have `scan_root`). `scan_*_with_occurrences` add observation
linkage. `scan_*_detailed` is the action API.

**Source outcome.** Use `SourceScan::failure()` instead of matching
`scanner_error` strings or inferring failure from `completion.is_none()`.
`coverage()` reports `WholeSource` or `Partial` (OpenCode).
`visibility_limits()` names the reasons for `VisibilityLimited`. Default bundled
scans of timed, session-scoped sources are now `Complete`: the Rule v1 `url`
target reads URL-keyed tool arguments instead of being unavailable, and the
`RuleTargetUnavailable` limit is removed. Session Event 3 can gain `url`
evidence for rules that target it. See
[Rule v1 URL target](../embedding.md#rule-v1-url-target).

**Action findings.**
- `session_event_index()` links an action to the Event 3 event projected for it
  (the session Rule v1 detection when it carries every rule of the action, or
  the process-chain event from the same result). Replace session-ID matching
  with it; handle `None`.
- Action DTOs no longer implement `Serialize`. Project accessors into a
  host-owned versioned envelope; compare with `==` (`Eq`) and inspect with
  `Debug`. The same applies to `RuleCatalogEntry`/`RuleCatalogKind` and to the
  unstable investigation `OccurrenceContext`/`ContextEntry`.
- `stage()` is `ObservationStage`, `kind()` is `ObservationFamily`, `severity()`
  (also on `CanonicalActionFinding`) is `Severity`, and `ActionContextEntry::kind()`
  is `ActionContextKind` with a new `stage()`. Use `as_str()` for the unchanged
  labels.
- `score()` is removed; use `promotion_score()`. It is neither native finding
  risk nor the Event 3 session score.
- Action and context `tool_name()` keep known built-in harness names readable
  (for example `Bash`); Event 3 is unchanged. Hosts that validated action tool
  labels with `terminal_historical_identifier("tool", …)` must switch to
  `terminal_historical_tool_label`, which accepts readable built-in names.

**Pipeline reuse.** `build()` compiles canonical semantics once; keep one
`Pipeline` rather than rebuilding per scan. A canonical rejection is now a
`build()` error rather than a later scan error.

**Acquisition errors.** `AcquisitionError`, `BoundedReadError`, and
`CanonicalBoundContext` are re-exported from core. New variants
`CanonicalBoundValidation { context }` (Codex bound failures) and
`CapabilityNotCompiled` (OpenCode without `opencode-sqlite`, previously
`SourceRead`) break exhaustive matches; add arms or a wildcard. A resumed
OpenCode read over its part limit reports `BoundedSourceRead(LimitExceeded)`
instead of `SourceRead`. `AcquisitionError` is now `#[non_exhaustive]`, so
matches need a wildcard arm. Its new `ResumeRegressed` variant reports a resumed
OpenCode read against a store older than the token.
`ObservationError` also exposes optional typed bound dimension/context; its
Display is unchanged. Event 3 adaptation stays generic.

**OpenCode feature.** The default core dependency graph no longer includes
`rusqlite`; enable `opencode-sqlite` to scan OpenCode. The CLI enables it.
See [OpenCode acquisition](../embedding.md#opencode-acquisition).

**Resuming OpenCode.** `scan_source_detailed_resuming` with a persisted
`ResumeToken` (from `SourceScan::resume_token()`) reads only parts updated since
the prior scan, with the CLI's overlap and limit. Hosts that rescanned the
bounded recent window on every change can switch; see
[resuming OpenCode scans](../embedding.md#resuming-opencode-scans).

**Record evaluation removed.** `Pipeline::detect_records`,
`Pipeline::evaluate_session`, the `telltale_detect::detection` module, and the
core re-exports of `NormalizedRecord`, `RecordKind`, `MatchResult`, and
`RiskAccountingError` are removed. They evaluated flattened records with Rule v1
outside the canonical path. Write a native session fixture (for example Codex
JSONL) and use `scan_sources_detailed`; see
[removed record evaluation](../embedding.md#removed-record-evaluation).

**Opt-in additions.** `telltale_core::inventory` (no rule compilation, no MCP
connection, no scan/watch emission) and
`SessionInvestigator::investigate_context` (content off by default, OpenCode
deferred) require no persistence migration.

These changes preserve the Event 3 schema, already-persisted Event 3 bytes,
state formats, CLI exit semantics, and rule validation order. Newly emitted URL
evidence can differ as described above. CLI diagnostics are unchanged except
one: an incremental OpenCode read over its part limit reports the scan summary
failure `acquisition_code` `source_limit_exceeded` instead of `source_read`.
The Event 3 `scanner_error` event for that failure is unchanged.

## What stays compatible

Event3 remains the sole production event/output contract for 0.7. The Event3
schema, consumer contract, terminal privacy boundary, event identity rules,
canonical JSONL behavior, and already-persisted Event3 bytes remain supported.

Existing non-Rust adopters should continue to consume canonical Event3 JSONL
rather than scrape scan diagnostics from stdout. Rust consumers can use
`telltale_schema::event::Event3Record` for one terminal Event3 object or
`telltale_core::LocalEventFeed` for bounded read-only local journal polling.

Rule v1 remains the supported content-compatibility format. Event4 is not a 0.7
production output and does not require an adopter migration.

## Production runtime change

The normal source-backed production path is now:

```text
source discovery
-> telltale_sources::acquisition
-> source-native extraction and native accounting/progress
-> Canonical Observation v2
-> Detection v2 (Rule v1 content and process-chain evaluation)
-> Event3 compatibility projection
-> output/durability/delivery
```

CLI scan/watch and every `telltale_core::Pipeline` scan method use that
canonical runtime.
Newly generated detections, evidence, hashes, or severity are
not required to be byte-identical to output from the retired legacy internal
runtime, even though the Event3 wire contract remains compatible.

The caller-provided record APIs `Pipeline::detect_records` and
`Pipeline::evaluate_session` are removed; see
[Rust embedding changes since RC1](#rust-embedding-changes-since-rc1).

## Supported source denominator

The 0.7 built-in source denominator is eight exact identities across six agent
families:

- Claude Code: `claude.projects`
- Codex: `codex.sessions`, `codex.archived_sessions`,
  `codex.headless_sessions`
- OpenCode: `opencode.sqlite`
- OpenClaw: `openclaw.agents`
- Qwen CLI: `qwen.projects`
- GitHub Copilot: `copilot.process_log`

The canonical [Source Validation Matrix](../source-validation-matrix.md) records
fixture and bounded live-validation status. Fixture-only source families remain
preview/experimental for live source-store use unless later qualified.

The following former source identities are retired and are not built-in
discovery/parser compatibility paths in 0.7:

- `gemini.tmp`
- `opencode.legacy_json`
- `opencode.project_json`
- `roocode.tasks`
- `kilocode.tasks`
- `codex.project_sessions`

Do not depend on those identities returning as aliases. Adding one back requires
a separately accepted source contract.

## Removed transitional source APIs

Source-backed legacy record projection and parser-registration machinery was
removed after canonical runtime activation. There is no production
Canonical-Observation-to-NormalizedRecord bridge and no source-backed
NormalizedRecord-to-canonical bridge.

The direct-record APIs that evaluated caller-supplied `NormalizedRecord` values
are removed too. Source integrations should target the documented
acquisition/embedding boundary instead of retired parser registrations,
source-backed flat-record projections, or record evaluation.

### Downstream Rust integrations

Event3 JSON consumers remain compatible. Rust source integrations should use the
`Pipeline` scan methods, not retired `parser::parse_source_records` APIs.
Adopters pinned to published RC1 have only `scan_root`. Event3 projections stay
session-scoped with `timeline_anchors`; per-action results come from detailed
scans.

A vendored or modified subtree can differ in dependencies, per-action event
handling, and scoring. Do not assume drop-in compatibility with upstream 0.7.
Consumer-defined occurrence scores are not upstream scoring semantics; re-test
integrations when updating pins. Telltale remains standalone and has no
downstream-consumer dependency.

## Bounded message evaluation APIs (#79)

This applies to development builds containing Issue 79, not the immutable
`v0.7.0-rc.1` artifacts. The standalone matcher and selector APIs are now fallible:

```rust
// CompiledMatcher
pub fn evaluate(
    &self,
    observation: &CanonicalObservationV2,
) -> Result<MatcherEvaluation, ProcessingError>;

// SelectorRegistry
pub fn resolve(
    &self,
    selector: SelectorId,
    observation: &CanonicalObservationV2,
) -> Result<SelectorResolution, ProcessingError>;
```

These types are exported from `telltale_detect::v2`, except
`CanonicalObservationV2` from `telltale_schema::observation`. Update direct callers
to propagate or explicitly handle the error before using `state()`, `value()` or
`presence()`. For example, in a function returning `Result<_, ProcessingError>`:

```rust
let resolution = registry.resolve(selector, &observation)?;
let evaluation = matcher.evaluate(&observation)?;
```

Do not convert exhaustion into absence or no-match. Valid canonical observations
can carry independently governed metadata beyond the semantic/local retention
budget, so selector resolution cannot promise infallibility. Standalone detector
evaluation keeps its existing `DetectorResult` signature and reports exhaustion
as `DetectorError`; source evaluation remains all-or-nothing.

The 256 MiB source work counter is independent of compatibility retention bounds.
When sharing `EvaluationWorkBudget` for diagnostic policy comparison, use
`is_exhausted()` to distinguish true work exhaustion from other
`ProcessingError::Bounds` failures. Only true work exhaustion discards an otherwise
successful authoritative source evaluation; other comparison failures remain
diagnostic. See [bounded long-message matching](../canonical-observation-v2.md#bounded-long-message-matching-79-development-after-rc1)
for text, retention, work, provenance and evidence contracts. Event3 output and
inference acquisition limits remain unchanged.

## Event and telemetry boundary

Event3 remains frozen and current for production output. Event4 4.0 types,
structural schema, validation, and canonical encoding exist only as a
non-production foundation in `telltale-schema`.

0.7 does not activate:

- Event4 runtime output
- Event3/Event4 dual emission
- runtime telemetry profiles
- generalized multi-schema `CanonicalPayload`
- a generic collector or public IPC transport

A future Event4 production path must project independently from accepted semantic
truth and satisfy explicit activation gates; it must not be introduced as an
Event3 conversion layer.

## Upgrade and rollback

Review [controlled development deployment](../controlled-deployment.md) for
backup and rollback. Its development-archive installer rejects RC package
versions; do not use it to install `0.7.0-rc.1`. Published candidate
qualification must use the exact Release artifacts and
[release-readiness gates](../release-readiness.md). Treat configuration, scanner
state, canonical JSONL, and optional durable-delivery state as a coordinated
upgrade/rollback set.

Development builds containing Issue 69 HEC response validation add outbox error
classes that older binaries cannot decode. Before adopting that change, follow
the [durable snapshot and rollback boundary](../telemetry-output.md#delivery-guarantees)
in Telemetry output; replacing only the binary is not a safe downgrade after
new delivery classifications have been persisted. This is a development change,
not a claim about the immutable `v0.7.0-rc.1` artifacts described above.

The current stable release is `v0.6.0` until a later stable GitHub Release is
published. An RC is immutable validation evidence, not a replacement for stable
release provenance.
