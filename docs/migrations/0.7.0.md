# Migrating to 0.7.0

Status: compatibility guide for published prerelease `v0.7.0-rc.1` (Release ID
`397543935`, source `e2386cb53454a8384449ea0729f0e3b71072006c`). Five-platform
native qualification passed in run `36305581215` using verifier tooling
`c5c955f57a83cbfc7bd9827932a5e7d54a2fd077`. Stable `v0.7.0` is not published;
clean-host qualification and stable promotion remain separate.

Development additions below are labeled separately. `Pipeline::scan_sources`
is current-development behavior on `main` after RC1, is not in the published
RC1 artifacts, and is not qualified by RC1 evidence.
The occurrence-aware `Pipeline::scan_sources_with_occurrences` and
`scan_root_with_occurrences` methods are also development additions after RC1.
They return precise observation associations alongside the same session-scoped
Event3 events, without a second detection pass; see [embedding](../embedding.md#detection-occurrences-current-development-after-rc1).
Updating a git pin and separate validation are required; this is not RC1
qualification.

### Optional OpenCode acquisition (current development after RC1)

The default core normal dependency graph no longer includes `rusqlite`.
Git-pinned OpenCode scanning hosts must explicitly enable the default-off core
`opencode-sqlite` feature, which forwards `telltale-sources/opencode-sqlite` and
uses bundled SQLite. The CLI enables it explicitly. Feature-off scans retain
JSONL successes and report OpenCode as a safe per-source `scanner_error`.
`protected-assignment` is independent. OpenCode investigation remains deferred
either way, before discovery, I/O, or process spawn. This requires host validation
after a Git-pin update, not RC1/stable qualification.
See [embedding](../embedding.md#opencode-acquisition-feature-current-development-after-rc1).

### Contextual investigation (current development after RC1)

Git-pinned hosts may opt into `SessionInvestigator::investigate_context(&request)`;
`investigate` stays content-free. Content defaults off, enabled text is redacted,
and tool results are excluded. This is not Event3 or RC1 qualification; updating
the pin requires separate host validation. No persistence migration or scan/watch
activation is introduced; OpenCode remains deferred. See the
[full embedding contract](../embedding.md#contextual-investigation-current-development-after-rc1).

### Inventory facade (current development after RC1)

Git-pinned hosts can opt into `telltale_core::inventory` for existing install
snapshots and privacy-projected static MCP config events without compiling rules
or connecting to MCP servers. Prefer explicit host-owned `InstallInventoryContext`
roots; `current()` and `collect_install_inventory` read the process environment.
This adds no scan/watch activation, `Pipeline` inventory emission, or persistence
migration. Update the pin and validate separately: this is not RC1/stable
qualification. See [embedding](../embedding.md#inventory-facade-current-development-after-rc1).

### Canonical bound diagnostics (current development after RC1)

`telltale_sources::acquisition::AcquisitionError` adds the public
`CanonicalBoundValidation { context: CanonicalBoundContext }` variant for Codex
bound failures. `CanonicalValidation { code }` remains available; both the new
variant's `code()` and Display return `unbounded_value`.
The optional `bound_context()` accessor returns only closed field-category and
bound-dimension enums. `ObservationError` also exposes optional typed bound
dimension/context; its Display stays unchanged.

Adding an enum variant is a Rust source compatibility break for exhaustive
matches: hosts must handle the new variant when updating their git pin. This is
not fully source compatible or RC1/stable qualification. Event3 bytes and scanner
error adaptation do not acquire diagnostic fields. See the
[diagnostic contract](../canonical-observation-v2.md) and
[embedding contract](../embedding.md#canonical-bound-diagnostics-current-development-after-rc1).

## What stays compatible

Event3 remains the sole production event/output contract for 0.7. The Event3
schema, consumer contract, terminal privacy boundary, event identity rules,
canonical JSONL behavior, and already-persisted Event3 bytes remain supported.

Existing non-Rust adopters should continue to consume canonical Event3 JSONL
rather than scrape scan diagnostics from stdout. Rust consumers can use
`telltale_schema::event::Event3Record` for one terminal Event3 object or
`telltale_core::LocalEventFeed` for bounded read-only local journal polling.

Rule v1 remains the supported content-compatibility format. Event4 is not a 0.7
production output and does not require an adopter migration.

## Production runtime change

The normal source-backed production path is now:

```text
source discovery
-> telltale_sources::acquisition
-> source-native extraction and native accounting/progress
-> Canonical Observation v2
-> Detection v2 (Rule v1 content and process-chain evaluation)
-> Event3 compatibility projection
-> output/durability/delivery
```

CLI scan/watch and `telltale_core::Pipeline::scan_root` use that canonical
runtime. On current-development `main` after RC1, `Pipeline::scan_sources` also
uses it; this method is not part of the published RC1 artifacts or qualification.
Newly generated detections, evidence, hashes, or severity are
not required to be byte-identical to output from the retired legacy internal
runtime, even though the Event3 wire contract remains compatible.

The caller-provided record APIs `Pipeline::detect_records` and
`Pipeline::evaluate_session` remain deliberate `NormalizedRecord`
compatibility surfaces. They are not the source-backed production acquisition
path.

## Supported source denominator

The 0.7 built-in source denominator is eight exact identities across six agent
families:

- Claude Code: `claude.projects`
- Codex: `codex.sessions`, `codex.archived_sessions`,
  `codex.headless_sessions`
- OpenCode: `opencode.sqlite`
- OpenClaw: `openclaw.agents`
- Qwen CLI: `qwen.projects`
- GitHub Copilot: `copilot.process_log`

The canonical [Source Validation Matrix](../source-validation-matrix.md) records
fixture and bounded live-validation status. Fixture-only source families remain
preview/experimental for live source-store use unless later qualified.

The following former source identities are retired and are not built-in
discovery/parser compatibility paths in 0.7:

- `gemini.tmp`
- `opencode.legacy_json`
- `opencode.project_json`
- `roocode.tasks`
- `kilocode.tasks`
- `codex.project_sessions`

Do not depend on those identities returning as aliases. Adding one back requires
a separately accepted source contract.

## Removed transitional source APIs

Source-backed legacy record projection and parser-registration machinery was
removed after canonical runtime activation. There is no production
Canonical-Observation-to-NormalizedRecord bridge and no source-backed
NormalizedRecord-to-canonical bridge.

Consumers that intentionally supply their own `NormalizedRecord` values may
continue to use the direct-record compatibility APIs. Source integrations should
target the documented acquisition/embedding boundary instead of retired parser
registrations or source-backed flat-record projections.

### Downstream Rust integrations

Event3 JSON consumers remain compatible. Rust source integrations should use
source-native acquisition/discovery and `Pipeline::scan_root` or, on a
current-development revision after RC1, `Pipeline::scan_sources`, not retired
`parser::parse_source_records` APIs. Adopters pinned to published RC1 must use
`scan_root`; `scan_sources` requires updating the pin and separate validation.
Hosts selecting stores can discover sources and pass exact `Source` values to
`scan_sources`; its Event3 projection remains session-scoped with
`timeline_anchors`, not per-action events.

A vendored, modified 0.6 subtree (including older `rusqlite` dependencies or
per-action events) is not drop-in compatible with upstream 0.7. Downstream
occurrence scores are not upstream scoring semantics; re-test the integration
when updating its pin. Telltale has no Emusary dependency and remains useful
standalone.

## Development after RC1: bounded message evaluation APIs (#79)

This applies to development builds containing Issue 79, not the immutable
`v0.7.0-rc.1` artifacts. The standalone matcher and selector APIs are now fallible:

```rust
// CompiledMatcher
pub fn evaluate(
    &self,
    observation: &CanonicalObservationV2,
) -> Result<MatcherEvaluation, ProcessingError>;

// SelectorRegistry
pub fn resolve(
    &self,
    selector: SelectorId,
    observation: &CanonicalObservationV2,
) -> Result<SelectorResolution, ProcessingError>;
```

These types are exported from `telltale_detect::v2`, except
`CanonicalObservationV2` from `telltale_schema::observation`. Update direct callers
to propagate or explicitly handle the error before using `state()`, `value()` or
`presence()`. For example, in a function returning `Result<_, ProcessingError>`:

```rust
let resolution = registry.resolve(selector, &observation)?;
let evaluation = matcher.evaluate(&observation)?;
```

Do not convert exhaustion into absence or no-match. Valid canonical observations
can carry independently governed metadata beyond the semantic/local retention
budget, so selector resolution cannot promise infallibility. Standalone detector
evaluation keeps its existing `DetectorResult` signature and reports exhaustion
as `DetectorError`; source evaluation remains all-or-nothing.

The 256 MiB source work counter is independent of compatibility retention bounds.
When sharing `EvaluationWorkBudget` for diagnostic policy comparison, use
`is_exhausted()` to distinguish true work exhaustion from other
`ProcessingError::Bounds` failures. Only true work exhaustion discards an otherwise
successful authoritative source evaluation; other comparison failures remain
diagnostic. See [bounded long-message matching](../canonical-observation-v2.md#bounded-long-message-matching-79-development-after-rc1)
for text, retention, work, provenance and evidence contracts. Event3 output and
inference acquisition limits remain unchanged.

## Event and telemetry boundary

Event3 remains frozen and current for production output. Event4 4.0 types,
structural schema, validation, and canonical encoding exist only as a
non-production foundation in `telltale-schema`.

0.7 does not activate:

- Event4 runtime output
- Event3/Event4 dual emission
- runtime telemetry profiles
- generalized multi-schema `CanonicalPayload`
- a generic collector or public IPC transport

A future Event4 production path must project independently from accepted semantic
truth and satisfy explicit activation gates; it must not be introduced as an
Event3 conversion layer.

## Upgrade and rollback

Review [controlled development deployment](../controlled-deployment.md) for
backup and rollback. Its development-archive installer rejects RC package
versions; do not use it to install `0.7.0-rc.1`. Published candidate
qualification must use the exact Release artifacts and
[release-readiness gates](../release-readiness.md). Treat configuration, scanner
state, canonical JSONL, and optional durable-delivery state as a coordinated
upgrade/rollback set.

Development builds containing Issue 69 HEC response validation add outbox error
classes that older binaries cannot decode. Before adopting that change, follow
the [durable snapshot and rollback boundary](../telemetry-output.md#delivery-guarantees)
in Telemetry output; replacing only the binary is not a safe downgrade after
new delivery classifications have been persisted. This is a development change,
not a claim about the immutable `v0.7.0-rc.1` artifacts described above.

The current stable release is `v0.6.0` until a later stable GitHub Release is
published. An RC is immutable validation evidence, not a replacement for stable
release provenance.
