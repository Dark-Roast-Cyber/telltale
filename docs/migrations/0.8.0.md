# Migrating to 0.8.0

Status: compatibility guide for the 0.8.0 line, in development. Release
identities and qualification results will be on each
[GitHub Release](https://github.com/Dark-Roast-Cyber/telltale/releases).
Upgrading from 0.6.x? Read the [0.7.0 migration guide](0.7.0.md) first.

## Rule v1 is replaced by Rule v2

Telltale rules are now written in Rule v2, Telltale's
[Sigma profile](../rule-format.md): one Sigma 2.1 document per rule or chain,
marked `taxonomy: telltale`, with Telltale semantics in a `telltale` block.

- **Rule v1 files fail to load.** Every rule file in
  `organization-rules.d`, `rules.d`, `ui-rules.d`, `--rules`, rule packages and
  documents passed to `Pipeline` must be Rule v2. A document with a top-level
  `version` key is Rule v1 and fails with "Rule v1 is no longer supported;
  rewrite this document as Rule v2: see docs/rule-format.md and
  docs/migrations/0.8.0.md", even when a higher tier replaces it or it is
  disabled; it is never skipped silently. There is no automatic converter: rewrite custom rules
  by hand with the table below, then check them with
  `telltale rules validate`.
- **Shipped content is already converted.** The bundled core rules and chains,
  the hooks self-protection rules and the example rules under `config/rules/`
  are Rule v2. Before Rule v1 was removed, a parity test proved each converted
  rule compiles to the same matchers, with the same behaviour fingerprint, so
  detections, rule IDs, Event 3.0 output and the core and hooks rule
  fingerprints are unchanged.
- **The community package changes once.** The embedded community package is
  its Rule v2 release (0.2.0). A v2 package orders its documents by name, and
  that order is part of the rule set's fingerprint, so the effective rule set
  fingerprint and semantic identity change once at this release even where a
  rule's matchers do not. `tdx.persistence.git_hook_change` now also matches a
  write to `.git/hooks/<name>` by its written path (sample hooks excluded), not
  only by command text.
- **Rule names are unchanged.** A Rule v1 rule `id` is the Rule v2 `name`, so
  overrides, policies, saved searches and Event 3.0 `rule_ids` keep working.
- **Process-chain packs are unchanged.** They are a separate internal format.

## Key mapping

| Rule v1 | Rule v2 |
| --- | --- |
| One document with `version: 1`, `description`, `defaults`, `rules:` and `modifiers:` | One YAML document per rule or chain, separated by `---`, each with `taxonomy: telltale`. A file-level description becomes a YAML comment. |
| Rule `id` | `name`, unchanged. |
| (none) | `id`: a new UUIDv4, generated once and kept. |
| `title` | `title`, now required. |
| `severity` | `level`. |
| `category`, `score`, `explanation` | `telltale.category`, `telltale.score`, `telltale.explanation`. |
| `detection_class`, `signal_type`, `analytic_intent`, `enabled` | The same keys under `telltale`. |
| `defaults.enabled` | `telltale.enabled` on each rule. |
| `tags` | `telltale.tags`. |
| `atlas_tags: ['atlas:AML.T0051']` | `tags: [atlas.aml.t0051]`. |
| `status`, `description`, `author`, `references`, `falsepositives` | The same keys. `status` is one of `experimental`, `test`, `stable`, `deprecated` or `unsupported`; the last two load disabled. `description` and `author` are plain text. |
| (none) | `logsource`: `product: ai_agent` and the `category` that fits the fields read. |
| Targets `command`, `arguments`, `written_path`, `file_path`, `tool_name`, `tool_kind`, `url`, `tool_result`, `assistant_context`, `user_context` | Fields `tool.command`, `tool.arguments`, `tool.written_path`, `tool.path`, `tool.name`, `tool.kind`, `tool.url`, `tool.result`, `message.assistant_text`, `message.user_text`. |
| `targets` with one `regex` | A list identifier `selection` with one `<field>\|re` item per target; a YAML anchor writes the pattern once. |
| `detection.selection` (one regex per target) | One selection per target, such as `selection_command` with `tool.command\|re`. |
| `detection.exclude` | A filter on the same field, such as `filter_command`, used as `selection_command and not filter_command`. |
| `defaults.case_insensitive: true` | `\|re\|i` on every value, filters included. Without it, `\|re`. |
| `detection.scope: segment`, `exclusion_segment`, `recorded_exclusion` | The scope modifier `\|segment`, `\|exclusion_segment` or `\|recorded_exclusion` on each selection key and its filter. |
| `condition: selection` | A condition that names every selection: `selection`, `1 of selection_*`, or an `or` of `selection_x` and `(selection_x and not filter_x)` terms. |
| Modifier `id` | Chain `name`, with a new `id` and a `title`. |
| `when_all_categories` / `when_all_rule_ids` | `correlation.categories` / `correlation.rules`, with `correlation.type: telltale_chain`. |
| `link.calls` | `correlation.within_calls`. |
| `link.order: declared` / `any` | `correlation.order: ordered` / `any`. |
| `link.minutes` | No Rule v2 spelling yet; a chain links by tool calls only. |
| Modifier `score`, `explanation`, `detection_class`, `signal_type`, `analytic_intent`, `enabled` | The same keys under `telltale`. |
| Modifier `atlas_tags` | `tags: [atlas.*]`. |

### A rule, before and after

<!-- rule-example: rule v1 -->
```yaml
version: 1
description: Local rules.
defaults: {case_insensitive: true, enabled: true}
rules:
  - id: example.download.curl
    title: Example curl download
    category: download
    severity: low
    score: 20
    targets: [command, arguments]
    regex: '\bcurl\b.*https?://'
    tags: [example]
    explanation: Example rule that matches curl downloads.
    detection_class: threat_hunting
modifiers: []
```

```yaml
# Local rules.
title: Example curl download
id: c56a4180-65aa-42ec-a945-5fd21dec0538
name: example.download.curl
taxonomy: telltale
logsource:
    product: ai_agent
    category: tool_activity
detection:
    selection:
        - tool.command|re|i: &pattern '\bcurl\b.*https?://'
        - tool.arguments|re|i: *pattern
    condition: selection
level: low
telltale:
    category: download
    score: 20
    explanation: Example rule that matches curl downloads.
    detection_class: threat_hunting
    tags: [example]
```

### A modifier, before and after

<!-- rule-example: rule v1 -->
```yaml
version: 1
description: Local chains.
defaults: {case_insensitive: true, enabled: true}
rules: []
modifiers:
  - id: example.chain.download_then_run
    score: 30
    when_all_categories: [download, execution]
    link: {calls: 2, order: any}
    explanation: A download followed by execution.
```

```yaml
title: Download followed by execution
id: 6fa459ea-ee8a-4ca4-894e-db77e160355e
name: example.chain.download_then_run
taxonomy: telltale
correlation:
    type: telltale_chain
    categories: [download, execution]
    within_calls: 2
    order: any
telltale:
    score: 30
    explanation: A download followed by execution.
```

## Replacing a bundled rule needs its `id`

A rule in `organization-rules.d`, `rules.d` or `ui-rules.d` still replaces the
rule with the same name from a lower tier, and it must now carry the same Rule
v2 `id` as the rule it replaces; a different `id` is an error. An `id` used
under two names is also an error. Start a replacement from
`telltale rules export-default`, which writes each bundled rule with its `id`,
and keep that `id`. See [identity and replacement](../rule-format.md#identity-and-replacement).

A replacement that changes a bundled rule's matchers no longer gets that rule's
built-in action profile; `telltale rules validate` reports the notice
`native_profile_not_applied`.

## A background `&` ends a segment

The `segment` and `exclusion_segment` scope modifiers now split a field where
a shell ends a statement: a background `&` and `|&` end a segment, as `;`,
`|`, `||`, `&&` and line breaks already did. The `&` of a redirection (`2>&1`,
`&>`, `>&2`, `<&3`) does not. A custom rule whose segment-scoped pattern
spanned a background `&` now sees each side as its own segment, so write its
selection and filter for one statement. See
[scope modifiers](../rule-format.md#scope-modifiers).

## The controlled-domain rule is split

`network.controlled_test_domain.darkroast` keeps its name, `id`, category
(`exfiltration`), level and 45 points, but now reads only a tool call's
`command`, `arguments` and destination `url`. Assistant text and tool results
that name the controlled tester domain raise the new rule
`network.controlled_test_domain.mention`: category `network_reference`,
level informational, 0 points, a hunt signal. A reference alone is not
treated as outbound communication, so it no longer supplies the
`exfiltration` step of a chain.

Who sees a change:

- A session that only names the domain in a message or tool result scores
  45 points less and loses any chain that step completed; it shows
  `network.controlled_test_domain.mention` instead.
- A tool call that requests a transfer to the domain is unchanged.
- A policy that disables `network.controlled_test_domain.darkroast` by name
  and wants no finding for references either should also list
  `network.controlled_test_domain.mention`. A policy that selects categories
  without `network_reference` already leaves it out.
- An organization rule that replaces the old rule by its `id` keeps its own
  matchers; review whether it should follow the split.

## Override reasons are bounded

An override entry's `reason`, in `overrides.d` or a builder override document,
must be at most 256 characters, and only tab and newline are allowed among
control and invisible formatting characters. A longer reason, or one with such
characters, now fails to load as an invalid override. Shorten it before
upgrading.

## At most 256 override entries per rule

The override entries applied to one rule, across all of `overrides.d` or a
builder's override documents, are now limited to 256. Content with more fails
to load: the CLI names the file that crosses the limit, and the builder fails
with `rule_content_exceeds_bounds`. Merge repeated entries for a rule before
upgrading: for `enabled` and for `score`, only the last entry that sets the field
takes effect.

## At most 256 rule packages and 3725 definitions

Loaded rule content is now limited to 256 rule packages, counting the embedded
community package, and to 3725 rules and chain modifiers after tiers merge:
with the 371 bundled process-chain rules, that fills a 4096-entry rule catalog.
Content with more fails to load, in the CLI and in hooks with a message, and in
the builder with `rule_content_exceeds_bounds`. Combine packages or retire
unused rules before upgrading.

## Rule packages use format v2

Rule packages use `format: telltale-rule-package/v2`. A v2 package is a YAML
stream: the first document is the header, which adds a required `title`, and
every following `---` document is one Rule v2 rule or chain, written as in a
rule file, sorted by `name`, each `name` starting with the package's
`rule_namespace`. The v2 header has no `documents` key: write each rule and
chain as its own document after the header. YAML anchor names must be unique
within a document. A format v1 package fails to load with an error that points
to this guide, and Telltale 0.7
does not read v2 packages, so a v2 community package needs Telltale 0.8.0. The
order of a package's documents is part of its rule set's fingerprint, so the
effective rule fingerprint changes once when a package is rewritten as v2. See
[rule packages](../rule-format.md#rule-packages).

## Rule catalog v2

`rule_catalog_document` and `Pipeline::rule_catalog_document` return rule
catalog v2 (`telltale.rule_catalog.v2`,
[schema](../../schemas/rule-catalog-v2.schema.json)): every catalog v1 entry
key with the same meaning, plus the Rule v2 metadata (`uuid`, `status`,
`description`, `references`, `author`, `license`, `date`, `modified`,
`related`, `logsource`) and two revisions, `behavior_fingerprint` and
`metadata_revision`. `telltale rules catalog` prints it for the resolved rules.
Catalog v1 is kept as a [historical schema](../../schemas/historical/README.md).
See [embedding](../embedding.md).

## Rust API

- `telltale_rules::bundled_default_rule_set()` is removed. Use
  `bundled_default_rules()` for the bundled rules as loaded content, or
  `load_default_rule_set()` for the compiled set.
- `LoadedRules::parse` reads one rule file, and `LoadedRules::merge` combines
  files additively; `CompiledRuleSet::notices()` lists load notices.
- `RulePackage::documents()` and `into_documents()` return `LoadedRules`.
- `Pipeline::builder()` gains `organization_rules_document` and
  `override_document`, with labelled variants, which take the CLI's
  `organization-rules.d` and `overrides.d` content as text. See
  [replacing rule content](../embedding.md#replacing-rule-content).
- A definition ID that two builder inputs repeat now fails with a
  `RuleContentError` whose code is `DuplicateId` (text
  `rule_content_duplicate_id`), the `source()` of
  `PipelineError::Compilation`. Before, the cause's text was
  `duplicate rule id: <id>`. Match the code, not the text.
- A `rules_document`, rule package or policy that does not parse now fails
  with a `RuleContentError` whose code is `InvalidDocument` (text
  `rule_content_invalid_document`) and whose `document()` is `explicit:<n>`,
  `package:<n>` or `policy:1`, as does one whose rule fails its own
  validation (Rule v1, an unknown field, an invalid pattern, an unsupported
  level). Before, the cause was untyped and its text was the load error. The
  CLI still prints the full message: run `telltale rules validate` on the
  same content to see which rule fails and why.
- `LoadedRules::apply_override_document` takes the document's name as `&str`
  instead of a path and an optional label, which each `AppliedOverride`
  records in its new `label` field, and returns `RuleOverrideError`.

## Over-bound tool values

A tool call or result with one value over its own canonical bound is no
longer dropped whole. The value alone is replaced, the call's other facts (tool
name, paths, other arguments) are evaluated, and nothing is derived from the
replaced value. A tool value within its own bound that the observation cannot hold together
with the call's other fields, or with the fields derived from its values, is
handled the same way: the largest tool values are replaced until the call
fits, and when that is not enough every tool value of the call is replaced.
A searchable text derived from a call (`tool.searchable_arguments`,
`tool.searchable_result`) that is over its own bound is omitted before the
values are fitted or replaced whole; values within their own bounds are kept
unless the cap on recorded replacements is reached. The unit is reported
with the target `searchable_arguments` or `searchable_result`, and a rule
condition that reads an omitted searchable text is not evaluated for that
call (insufficient visibility) rather than read as absent.
Selectors over bounded tool values report unavailable visibility the same
way: `tool.arguments` and `tool.result` with a replacement, and a text or
fact read from them that is absent while its field has a replacement, are
not evaluated. A URL or written-path list read beside a replacement is
partial (`SelectorResolution::is_partial`): a match on it counts as it did
before, and a no-match or a negated condition is not evaluated. Argument
keys stay exact beside a replaced value and are partial only when a member
was dropped for an over-long key.
A string whose normalized form is over its bound counts as over it. Messages, and failures that are not a
value bound, are still quarantined; hook journals keep strict conversion.

- **Scan summaries.** `source_processing` gains `bounded_value_unit_count`
  and `bounded_value_units` (every entry of up to 1,000 units, as `{source,
  session_id, native_id, source_sequence, target, dimension}`, coordinates
  only; a count above the distinct units listed means the list was cut). These
  units no longer count in `quarantined_unit_count`. Either makes
  `selected_source_coverage` `partial`.
- **Scanner errors.** Each evaluated window with replaced values emits one
  content-free `scanner_error` whose `error` evidence is
  `canonical_values_bounded`, unless a unit of the same window was also
  quarantined, in which case it keeps `canonical_units_quarantined`; a
  source drained in several windows can emit both. Accept the new value
  wherever you map scanner error codes.
- **Legacy OpenCode.** A legacy OpenCode source with a tool value over its
  own bound, or with tool values it cannot hold together, no longer fails
  and holds its cursor: the values are replaced, the
  source is evaluated and its cursor moves on. A call that cannot be held
  even with its values replaced keeps today's handling.
- **New detections and identity.** Sessions holding such calls can produce
  detections they did not before. An incremental scan does not revisit units
  its state already covers; use fresh state or `--history all` to evaluate
  them. The native action profile changes in this release, so
  `semantic_identity` changes and replay identities do not: rebaseline as
  after a rule change.
- **Embedders.** `SourceScan::bounded_units()` lists the units by coordinates
  (`BoundedUnit`), and `QuarantinedUnit` is unchanged. A host that builds a
  `ToolObservation` by hand with authored text (a command, file body or
  patch) over the structured string bound must declare that field with
  `with_argument_text`, or validation refuses the observation.
  `try_from_source_tool_arguments` takes an `ArgumentText` declaration
  instead of a tool name. `ToolObservation::with_fitted_values` and
  `with_replaced_values` replace a converted call's values the same way, and
  `with_bounded_values` keeps the observation's cap on replacements by
  replacing whole the field with more of them.
  `with_bounded_searchable_arguments` and `with_bounded_searchable_result`
  set a searchable text, or omit one over its bound and record it.
  `BoundedTarget` has four variants (`Arguments`, `Result`,
  `SearchableArguments`, `SearchableResult`); match it with a wildcard arm
  if you only handle tool values.

## Before adopting 0.8

1. Rewrite every custom rule file and package as Rule v2.
2. Give each rewritten rule a new UUIDv4 `id`, except a replacement of a
   bundled or package rule, which keeps that rule's `id`.
3. Run `telltale rules validate` (or `telltale config validate`) against the
   deployed configuration roots, and review `notices`.
4. Compare `telltale rules list` with the output of the previous release: the
   rule names, categories, severities and scores should match.
