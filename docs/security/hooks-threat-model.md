# Telltale Hooks threat model

What a pre-execution hook (`telltale hooks`) can and cannot guarantee. This
page is part of the [Telltale threat model](threat-model.md) and covers only
the hooks integration ([overview](../hooks/README.md)). It names residual
risks by category. It does not list the concrete forms that still evade
detection; those are tracked privately under the [security policy](../../SECURITY.md).

Each item has a status: **Mitigated**, **Partial**, **Accepted** (documented
residual risk), **Open** (tracked), **Upstream** (needs a change in the
embedded detection library) or **Out of scope**. Regression tests pin the
mitigated and partial decisions (`crates/telltale/tests/hooks/`,
`tests/cli/hooks_*.rs`). Real-harness results are historical reports in
[`docs/hooks/e2e/`](../hooks/e2e/).

## What the hook sees

The hook sees what the harness reports: the tool name and input it is about
to run, and later the result it reports. It does not see OS-level effects. A
`requested` call is never proof of execution, and a `completed` report is the
harness's claim, not an independent observation.

Hooks run inside the same executable, OS user and file permissions as the
agent's other processes unless an operator deploys them otherwise. Anything
the agent can write as that user, it can try to tamper with. Managed
deployment (settings the agent cannot override, state outside the agent's
reach) is the control that closes this class; the items below are
defense in depth on top of it.

## Detect-only mode

Hooks are detect-only unless the configuration was read and says
`hooks.mode: enforce` ([overview](../hooks/README.md#detect-only-and-enforce)).
In that mode the guarantee is the reverse of the rest of this page: the hook
must not stop a call. One gate releases every answer, and in detect-only mode
it releases nothing: no decision on stdout, exit status 0, and an exit after
20 s for a hook that has not finished. It is settled from the configuration
before the payload is read, so tool input, an unreadable payload, a failure
policy of `deny`, a session lock that stays taken, and a panic cannot change
it. Tests pin this on every entry point (`tests/cli/hooks_unreadable_payloads.rs`,
`crates/telltale/src/hooks/gate.rs`).

Residual ways a detect-only installation can still stop a call, all outside
the hook process: the hook command cannot start (missing binary) on a harness
that blocks on a failed hook, an operator-set hook timeout under 20 s together
with a block-on-failure option, and the optional Codex exec-policy file, which
Codex applies natively.

Everything below describes an enforcing hook. In detect-only mode the same
detections are recorded and the verdicts are not returned.

## Agent-controlled bypasses

| Bypass | Status | Notes |
| --- | --- | --- |
| Edit or delete hook configuration (Claude Code, Copilot CLI and Codex CLI hook files, the exec-policy backstop, managed settings, custom harness homes, the installed binary) | Partial | Rules deny native write tools and normalized patches aimed at those files and commands that name a protected path together with a writing program or redirection, across POSIX, cmd.exe and PowerShell spellings, including quote-split and other spellings Telltale's shell reading resolves. A writing program counts at command position (start, after a separator, or behind a recognized wrapper), and a plain writer's target must be in its own command. What cannot write is not denied (reads, read pipelines, dry runs, `git` readers, commit and pull-request text, project-level directories, container flags); any other mention asks. Rules for a custom `CODEX_HOME` or `COPILOT_HOME` and for the running binary are generated from the hook's own environment. |
| Spell the protected path or the writer in a way the deny rules do not list | Partial | Fail-safe rules ask, with no list of wrappers or spellings, when a protected directory appears in any form together with a writer word, or a harness launch appears with a hook-disabling option, anywhere in the command. The cost is false asks on commands that only look like tampering, which are refusals on harnesses that cannot ask. Telltale adds the points of every rule that matches one call, so two different asking rules can reach a deny. |
| Assemble the path or command at run time, or hide it in authored content | Accepted, Upstream | Pattern rules cannot resolve every shell or interpreter semantics, and authored file content is not visible to rule targets. Encoded forms are scored for review by bundled content. A regression test pins the accepted set privately. The real fix is managed settings plus state outside the agent's reach. |
| Stage a hook-free configuration elsewhere, then move it into place; write through an alias created earlier | Partial | The move or link into place is denied; the staging write and a later write through an alias are indistinguishable from ordinary writes. |
| Relaunch the harness without hooks, or point the hook at the agent's own configuration or state | Partial | Rules deny the harness's hook-disabling launch options and a command that launches a harness with a config or state home of its own or a Telltale variable that the hooks read (`TELLTALE_HOOKS_STATE_DIR`, `TELLTALE_HOOKS_TELEMETRY`, `TELLTALE_COMMUNITY_RULES`, `TELLTALE_PROCESS_CHAIN_DETECTIONS`); any other `TELLTALE_*` variable on a harness launch asks. The Codex forms are covered only by the optional exec-policy backstop, which refuses plain launches natively while its file exists and which indirect launches escape. |
| Switch enforcement off: set `hooks.mode` to detect-only, or damage or delete the configuration so that it no longer says `hooks.mode: enforce` | Partial | Enforcement is one setting in a file the agent's OS user can usually write, and the user's config root wins over `/etc/telltale`. The self-protection rules deny writes to the config roots and commands that modify them, and a configuration that still says `hooks.mode: enforce` but no longer loads denies tool calls. A configuration that is deleted or no longer says so is detect-only: the hook cannot tell that from an operator who never enabled enforcement. Keep the configuration in a root the agent cannot write and name only that root with `--config-dir` on the hook command. With a pinned user root (next row), a deleted root is invalid configuration, not the defaults in silence: tool calls are denied when the hook command carries `--expect-enforce`, otherwise a `config_invalid` record. |
| Move the config lookup: launch a harness with `XDG_CONFIG_HOME` or `HOME` (on Windows also `USERPROFILE`) changed, emptied or removed | Partial | A user-level install finds its settings in the user config root these variables name. A hook that reads another root, or none, loses `hooks.mode: enforce`, custom rules and raised policies together and is detect-only on the bundled rules, with no record. The system root (`/etc/telltale`, `%ProgramData%\telltale`) does not move, so a managed install that declares enforcement there keeps it. `telltale hooks <harness> settings` pins the user root on the hook command (`--user-config-dir`, quoted for the harness's shell) when that root exists, in its place after the system root, so the environment no longer moves it; a root that did not exist then is not pinned, and stderr says so. `check` lists each root it read, whether the user root is pinned, and whether it exists. When the configuration read at generation time enforces, the command also carries `--expect-enforce`, so a configuration that later does not load (the pinned root deleted included) denies tool calls with `config_invalid` instead of falling to detect-only; the marker never enables enforcement for a configuration that loads. Hook commands generated before the pin must be generated again to get it, and an install switched to enforce after its settings were generated has no marker until `settings` is run again: until then a configuration that does not load is detect-only with a `config_invalid` record, unless a remaining settings file says `hooks.mode: enforce`. Until then, or where a root cannot be pinned (a Windows path holding a quote), the self-protection rules deny launching a harness with these variables set inline or exported, removed (`env -u`, `env --unset`, `unset`, PowerShell `Remove-Item Env:`), or in an emptied environment (`env -i`, `env -`, `exec -c`); launch forms those rules do not recognize still move the lookup. |
| Move the state lookup: launch a harness with `TELLTALE_HOOKS_STATE_DIR`, `XDG_STATE_HOME` or `HOME` (on Windows `LOCALAPPDATA`) changed | Partial | The journal, session state and the default telemetry file live in the state directory these name. A hook that uses another one starts the session with no history, so cross-call chains and cumulative session risk restart, and writes its records elsewhere; one that resolves no directory is `state_dir_unresolved` (failure table). `telltale hooks <harness> settings` pins the state directory in use on the hook command (`--state-dir`, quoted for the harness's shell); a command that names its own config roots gets the directory those roots configure. With the flag, neither the variable nor the locating variables are consulted, and it replaces `hooks.state_dir` too, so a later change to either takes effect when `settings` is run again. A pinned directory that is missing is created owner-only; one that cannot be used gets the stricter of `on_error` and `on_unevaluable` (session files row), never a location the environment names. `check` shows the state directory and whether it is pinned. Hook commands generated before the pin must be generated again to get it; until then, or where the directory cannot be pinned (a Windows path holding a quote, or a command whose own config roots cannot be read plainly, which `settings` reports), the self-protection rules deny launching a harness with these variables set, as for the config lookup. |
| Change the self-protection rules through rule content or policy (a rule document, package, override or policy file in a config root) | Mitigated | While `hooks.self_protection_rules` is on, the `tth.tamper.` IDs belong to hooks: rule content that names one, or a policy under which any self-protection rule would not stay enabled, is invalid configuration, and the pipeline that is built must carry every self-protection rule, enabled and as its document defines it, or it does not build. Turning the rules off is the explicit, operator-level choice. |
| Tamper with journal, state or telemetry (same OS user) | Partial | Rules cover the default and resolved locations, and directories are owner-only on Unix. Deleting state resets cumulative session risk, and deleting the journal blinds cross-call chains; action-level findings are unaffected. Guaranteed: an unparseable ledger is quarantined and the call is still evaluated; files the hook cannot read or write get the stricter of `on_error` and `on_unevaluable` (default `ask`) and an `error` record, so with defaults this is never a silent allow. Runtime files are opened only as regular files (no symlink or FIFO is followed or blocks the hook). Operator inputs may be symlinks but must resolve to regular files. Tampering signals are emitted as `error` records. |
| Pad or nest a tool input so Telltale quarantines it | Partial | The input is flattened and chunked into bounded variants, and every byte is evaluated in at least one of them. Variants are packed to the bounds Telltale checks one call against (members, key and string bytes, and the encoded size of the whole input, counted escaped and normalized as Telltale counts it), so values that are too large together are spread over several variants rather than put in one that Telltale would refuse. A URL whose host holds a control character, which Telltale refuses, is evaluated with the control characters replaced. A finding in any variant keeps its force, so a deny found in one variant is not lowered by another variant that could not be evaluated. Each variant is evaluated as a call of its own, so what a rule needs together must be in one variant: short top-level values (paths, URLs, ordinary commands, and the names of flattened members) accompany each other and every other value and chunk, a top-level array of plain values keeps its name and array form (an argv is joined into one command), and a later chunk of a command starts with the head of that command. Where that cannot be kept, the verdict is floored at `on_unevaluable` and the record says `pending_input_separated`: more short top-level values than the variant budget can pair up, a command that had to be split, more than one command member (Telltale reads them as one command text, so each is evaluated in variants without the others), or a URL that had to be rewritten. A call whose input exceeds the projection budget (more values, or more bytes, than the bounded number of variants a call may take can hold) is evaluated on a bounded set of variants: a short command and the first block of short top-level values go with every variant, every chunk of a longer command (up to its own chunk limit) is evaluated ahead of other values, whatever the member names sort as, and then the start of other values while variants remain. The rest is unprojected and floors the decision at `on_unevaluable`, so "no finding" is not an allow there either; a finding in what was evaluated keeps its force. Residual: a rule that needs two long values together, values below the top level together, or far-apart parts of a long value that is not a command, can miss on a projected call; a split command can fall from a deny to the floor. Concrete forms are tracked privately. The floor costs asks on benign calls that are rare: a command above about 64 KiB or holding a URL above 4 KiB, a command above 3,000 bytes in a call projected for another member, and a call with more than about a hundred short top-level members. Large file content alone does not ask. |
| Craft identity fields (call key, session ID, tool name) so Telltale rejects the journal source | Mitigated | Unsafe values are replaced by a stable digest-based stand-in before journaling, telemetry keeps the raw value, and a call whose tool name had to be encoded is floored at `on_unevaluable` because name-routed rules cannot match the stand-in. Some malformed names remain a residual that is tracked privately. |
| Model-controlled tool input that makes Telltale reject the journal source | Mitigated | Input keys that Telltale would fold together are renamed in the evaluation encoding, so no value is lost. A scan that still fails at source level is retried on a reduced window, and a call that is too large on its own is scanned piece by piece within a time limit. The call keeps its rule verdict, and telemetry records the limit that applied. Exceptions that depend on load or queuing (a lock timeout, a very large call past the piece limit) get the stricter failure policy. Padding within the projection budget cannot lower a deny that a rule finds in the call, under any `on_unevaluable`; where the floor applies (this row's exceptions, and a projection that had to separate values, in the row above) it cannot turn a deny or an ask into an allow either. For a deny that only the unprojected remainder of a call past the projection budget holds, and for the residual of the row above, a deny can fall to `on_unevaluable`. See the failure table. |
| Oversized or malformed PreToolUse payload | Mitigated | Answered on stdout with the stricter of `on_error` and `on_unevaluable`; stdin is drained so the harness never sees a broken pipe. |
| Make the hook miss its timeout | Partial | A timed-out hook is killed and the call runs unless the harness has a block-on-failure option (`settings --fail-closed` enables it where it exists). The agent cannot slow a hook from inside a tool call except by stalling the evaluator (mitigated below). |
| Plugin or extension mechanisms that override hook blocks | Open | Reported by harness documentation, unverified. Managed settings mitigate. |
| Indirection: write a script with a benign call, run it later | Partial | Telltale evaluates each command; written-path rules and download/execute chains catch some forms. Authored content is not visible to rule targets. |
| Split a risky action across many low-scoring calls | Partial | Telltale chains plus the host session ledger. The window is bounded; chains older than the window are not reconstructed. A tool call's request costs the window at most one record of about 16 KiB, the size of the largest call Telltale evaluates whole, whether it was evaluated whole, projected or refused as unevaluable; so about 125 maximum-size requests fill the default window (2 MiB, 256 records), and their results take room too, each prompt or result at most `max_result_bytes` as the journal encodes it. A call's command is kept first in its record. A record longer than the whole window, as an older version could write, is skipped instead of emptying it. |
| Subagent delegation | Mitigated | Subagent calls hit the same hooks and share the session journal. |
| Tools not covered by hooks | Partial | Some harness paths never fire a pre-execution hook (documented per harness in the capability matrix). MCP and web tools do fire. |
| Prompt injection via tool results | Partial | Results are journaled and evaluated; findings add advisory context and raise session risk. |
| Learn the rules from deny reasons | Mitigated (opt-in) | By default reasons name rule IDs and thresholds. `reason_detail: minimal` keeps only the verdict kind and a record ID; use it where the agent is the adversary and runs unattended. |
| Impersonate the evaluator (plant a socket that answers "no opinion") | Mitigated for other users | The socket and its directory must belong to the same UID and not be group- or world-writable, and both ends check peer credentials. The same OS user can still replace the socket, as with any same-user state. |
| Stall the evaluator so other hooks time out | Mitigated | Per-connection reader threads with a total deadline, capped connections, deadlines on requests, and the stricter failure policy for an unanswered pre-execution request. |
| A path value that breaks the generated rule document | Mitigated | Paths from the environment and the configuration reach the generated self-protection rules. A character the YAML reader refuses used to fail the whole document, so no pipeline built and, with no operator rule files, calls were allowed by default; line breaks were folded and the rule never matched. Generated rules now write every such character by its code point, and any pipeline that does not build gets the stricter failure policy. A path too long for one rule, and its spelling from the user's home (`~`, `$HOME`), is matched by its last bytes, and `check` lists it. A path that is not UTF-8 still gets no generated rule. |
| Keep a stale evaluator serving old rules after an upgrade | Mitigated | The evaluator fingerprint covers the package version, the executable's build metadata and file identity (unique to the process when the file cannot be read, so nothing matches it), the configuration, referenced rule bytes and every path input; on a mismatch the evaluator retires. |
| Windows: no evaluator transport | Open | Hooks evaluate in-process with the same verdicts, slower, and never fail open. |
| Windows: reparse points, directory ACLs and path normalization | Partial, unverified on Windows | Runtime files are opened without following reparse points. State directories inherit the parent's ACL (the default is per-user). The system config root `%ProgramData%\telltale`, its folders and files are read only when owned by and writable only by Administrators, SYSTEM or TrustedInstaller and not links; a root another user created or can write fails the load (tested against real ACLs on Windows CI). The installed binary and harness drop-ins are not checked yet; that belongs with managed deployment. Generated path rules are literal on the native path; static rules carry the common Windows spellings. |

## Failure-induced bypasses

Wherever this table says `ask`, a human sees the prompt only where the harness
puts an ask to one in that run; a harness or run mode that cannot ask is given
a `deny` instead, and a headless run treats an ask as a denial.

| Condition | Default | Option |
| --- | --- | --- |
| Hook crashes, times out or is missing | Claude Code fails open; Copilot CLI blocks on crash or missing binary and runs the call on timeout; Codex CLI fails open with no option | `settings --fail-closed` where the harness supports it. For Codex, managed hooks are the real fix and the exec-policy backstop only refuses plain nested launches |
| The program at a trusted Codex hook path is replaced | Trust is kept (the hash covers the command text); the replacement runs as the hook | Keep the binary where the agent cannot write |
| The scan call itself returns an error (a scan or provenance failure, or no result). No input is known to cause these, and none is known not to | Stricter of `on_error` and `on_unevaluable` (default `ask`); `error` record | Raise either |
| No state directory resolves (for example an empty `HOME`, which an agent can set on a harness it launches) | On Unix the call is evaluated alone, in a fresh owner-only directory under the temporary directory that is removed afterwards: a rule's verdict holds, and a call with no finding gets the stricter of `on_error` and `on_unevaluable` (default `ask`), because it was evaluated without its session's history; the decision record says `state_dir_unresolved`. The raw input sits in that directory, at a location the environment chooses, for the length of the evaluation. Where that directory cannot be created, and always on Windows (no owner-only directory can be made there), the call is not evaluated and gets the stricter policy, a rule's deny included; `error` record. With no telemetry path configured either, nothing can be recorded and one line on the hook's stderr says what was decided. Other events are only recorded, not evaluated. `check` fails in that environment | Raise either; set `hooks.state_dir` |
| A scan fails at source level (Telltale rejects the window) | The window is reduced and the call keeps its rule verdict, except on a lock timeout; a call with no finding gets its plain verdict; `history_lost` on the record | none needed |
| A pending call fails at source level on its own | Scanned piece by piece for a bounded time: findings count, floor at `on_unevaluable` (default `ask`), `pending_pieces_unscanned` on the record if pieces were left; not evaluated at all: `on_unevaluable` | Raise or lower `on_unevaluable` |
| A file in a config root's `settings.d` or rule folders that is not a regular file at configuration load, or a `--config-dir` or pinned `--user-config-dir` folder that is missing | Invalid configuration: tool calls denied when a settings file says `hooks.mode: enforce` or the hook command carries `--expect-enforce`; otherwise detect-only on the defaults with a `config_invalid` record | none (deliberately loud while enforcing) |
| Rule content that names a self-protection rule ID, or a policy under which a self-protection rule would not stay enabled, while `hooks.self_protection_rules` is on | Invalid configuration: tool calls denied when a settings file says `hooks.mode: enforce`; otherwise detect-only on the defaults with a `config_invalid` record; `check` names the file | none (deliberately loud while enforcing) |
| Referenced rule content unreadable after load, or any rule pipeline that does not build (the reason names `telltale hooks check`) | Stricter of `on_error` and `on_unevaluable` (default `ask`); `error` record | Raise either |
| Session files unreadable or unwritable | Stricter of `on_error` and `on_unevaluable`; `error` record | Raise either |
| Session ledger unparseable or from another version | Quarantined and reset; the call is still evaluated | none needed |
| Tool input cannot be evaluated even after projection | `on_unevaluable: ask` | `deny`, or `allow` (not recommended) |
| Tool input is evaluated as a projection that had to separate values or parts of a command a rule may need together, or past the projection budget on a bounded set of variants | Findings count, floor at `on_unevaluable` (default `ask`); `pending_input_separated` on the record, or `pending_input_truncated` past the projection budget | `deny`, or `allow` (not recommended) |
| Hook payload unusable, tool call (including a named tool call without its tool input key; an empty input is evaluated) | Stricter of `on_error` and `on_unevaluable`, on stdout; denied when a configuration that asks for enforcement did not load | Raise either |
| Hook payload unusable, other named event | Exit 1 whatever `on_error` says: a block on a stop event would prompt the model without limit | none needed |
| Hook payload names no event | When the stricter of `on_error` and `on_unevaluable` is `ask` or `deny` (the default is `ask`), or a configuration that asks for enforcement did not load: each harness's block that needs no event, since such a payload cannot be asked about (residual on stop events for Claude Code). Exit 1 only when both allow | Set both to `allow` |
| A batch settles a call before its result arrives | Settlement is provisional; a later result supersedes it and reports `violated` for a denied call | none |
| Invalid configuration where a `settings.d` file says `hooks.mode: enforce` (read leniently, file by file: the one key, or any `mode: enforce` pair if the file is not YAML) | Tool calls denied | none (deliberately loud) |
| Invalid, missing or unreadable configuration where no `settings.d` file says `hooks.mode: enforce` | Detect-only on the defaults; `config_invalid` record and stderr | Fix the configuration |
| The hook panics | While enforcing, a panic is answered like a payload the hook could not read, with an `error` record (`hook_panicked`) that cannot change the answer: a tool call gets the stricter of `on_error` and `on_unevaluable` on stdout, a payload lost to the panic gets the nameless block, other events exit 1. A panic while loading the configuration is a configuration that did not load. The evaluator leaves a panicking connection unanswered (its client evaluates in-process) and retires, so the next hook starts a fresh one. Builds that abort on panic do not compile | Raise either |
| Evaluator unreachable, untrusted, or on another configuration | In-process evaluation (correct, slower) | `hooks.evaluator.enabled: false` |
| Evaluator received the request but did not answer before the deadline | The decision it recorded, if any; otherwise in-process evaluation, which keeps the rule verdict unless that times out on the session's lock | none |
| A session's lock stays taken for the 10 s a call waits, or until the hook's deadline if that comes first (`state_lock_timeout`) | Stricter of `on_error` and `on_unevaluable` (default `ask`); `error` record | Raise either |
| A call reaches the hook's 25 s deadline. Every wait is cut to what is left of that one deadline; one scan already in flight is not interrupted, so a single slow scan can still run past it and into the harness's timeout, which runs the call | No time left before the evaluation starts: not evaluated, no decision recorded, nothing journaled; stricter of `on_error` and `on_unevaluable` (default `ask`); `error` record (`hook_deadline`). A decision already evaluated is always delivered | Raise either |

## Confounds in testing

Model-side safety classifiers stop some obviously malicious commands before
any tool call reaches the hook. The real-harness suite attributes every
blocked canary to `hook` or `upstream_of_hook` and uses deterministic marker
rules to test enforcement independently of model refusals.

## Out of scope

General EDR, kernel or network enforcement, and sandboxing. Those are
complementary layers.
